> **The substrate executes the judge; it is not itself the law.**

This is a drafting commission, not permission to manufacture the missing evidence.

## 5. Required structure of the principal charter

`LANGUAGEHOOD-AND-SUCCESSION-CHARTER-0-R0.md` must contain, at minimum, the following sections.

### A. Status and non-self-ratification

State prominently that R0 is a **candidate**. It may propose holdings, but it does not adopt itself. Use a visible status legend that distinguishes at least:

- **ADOPTED LAW** — already owner-ratified and governing;
- **ACCEPTED EVIDENCE** — an empirical or documentary result accepted under its recorded ceiling;
- **PROPOSED HOLDING** — this charter's recommended interpretation awaiting owner ruling;
- **OPEN** — not yet established;
- **REFUSED CLAIM** — a formulation not licensed by present evidence;
- **HISTORICAL** — accurate to its period but not a present-state authority.

Do not label the proposed languagehood conclusion “adopted” anywhere in R0.

### B. Jurisdictional thesis

Explain the difference among:

- the host reader/compiler/runtime;
- the implementation of the Lisp+ judge/evaluator;
- the Lisp+ normative specification;
- a Lisp+ source form or program;
- an observed execution trace or outcome;
- an evidential claim made about that outcome.

The charter must state clearly that implementation in Common Lisp does not, by itself, collapse Lisp+ semantics into ordinary Common Lisp semantics. Conversely, do not pretend that syntactic resemblance or a specification document alone proves a functioning separate language. Tie the proposed holding to the actually adopted syntax, validation, operational semantics, refusal behavior, and observable consequences.

### C. Defined vocabulary

Define the following terms so that later claims can be mechanically classified rather than rhetorically admired:

- **host expressibility**;
- **semantic jurisdiction**;
- **normative syntax** and **well-formedness**;
- **operational semantics**;
- **observable consequence**;
- **languagehood**;
- **language distinctness**;
- **embedded language / hosted language**;
- **program expressibility**;
- **semantic prediction**;
- **semantic transmission**;
- **conformance** and the scope of a conformance claim;
- **implementation independence**;
- **independently seeded implementation**;
- **substrate independence**;
- **author independence**;
- **audit independence**;
- **model-family independence**;
- **independent inhabitation**;
- **generic authoring**;
- **open-ended authoring**;
- **language succession** and **successor language**;
- **fitness for latent-space machines**.

Definitions must include exclusion clauses. For example, conformance to a finite vector set is conformance **to that set and the behaviors it covers**, not a proof that every normative case is implemented correctly. Independent inhabitation by one author is not automatically generic authoring. A second implementation on Common Lisp may establish implementation independence while leaving substrate independence open.

### D. Independence topology

Provide a matrix that treats the following as separate axes:

| Axis | Question to answer |
|---|---|
| Author independence | Was the program author outside the language-construction loop and relevant prior solutions? |
| Implementation independence | Was the evaluator independently designed and coded without deriving from the reference implementation? |
| Substrate independence | Does the semantics travel to a genuinely different implementation substrate? |
| Model-family independence | Are relevant authors/reviewers from sufficiently separate training/model lineages for the claim being made? |
| Audit independence | Did the reviewer or validator lack the shared construction roots that would compromise the asserted audit? |

For each completed campaign, mark each axis **YES**, **NO**, **PARTIAL**, **NOT TESTED**, or **NOT APPLICABLE**, with a citation and a short rationale. Never turn “different model name,” “fresh context,” “held-out program,” or “different provider” into a universal independence token. Independence has dimensions; make every coin show its mint.

### E. Evidence-to-claim ladder

Construct a runged ladder that classifies at least these propositions:

1. Lisp+ has a specification-owned normative layer.
2. Lisp+ is distinct from ordinary Common Lisp evaluation in semantic jurisdiction.
3. Lisp+ qualifies as a small experimental hosted/embedded language.
4. The frozen R1 surface expressed the accepted Many Acts /0 succession specimens.
5. The public materials transmitted intended semantics under the precise P5 conditions actually achieved.
6. Lisp+ has portable conformance across independently seeded implementations.
7. Lisp+ has been independently inhabited.
8. Lisp+ supports generic or open-ended authoring.
9. Lisp+ qualifies as an independently implemented Lisp successor.
10. Lisp+ is especially suited “for latent-space machines.”

For every rung, state:

- current status;
- governing or evidentiary sources;
- exact ceiling;
- dependencies on lower rungs;
- what evidence would cross it;
- what evidence would **not** cross it;
- whether the charter recommends owner ratification now, deferral, or refusal.

My expected R0 recommendation, which you must test rather than merely echo, is:

- languagehood and semantic distinctness are evidentially crossed and suitable for owner ratification as a **small experimental hosted language**;
- the R1 expressibility/semantic-transmission finding is real but bounded by its recorded same-author/shared-construction conditions;
- portable conformance, independent inhabitation, generic/open-ended authoring, independently implemented succession, and the latent-machine comparative claim remain open.

If your source-grounded reading differs, say so exactly and put the divergence before the owner. Do not harmonize it into decorative unanimity.

### G. Admission gates and failure semantics

Define prospective admission gates for higher rungs. Each gate must specify:

- required exposure fence;
- allowed and forbidden source materials;
- preregistration requirements;
- subject identity and independence dimensions;
- normative oracle or frozen vector identity;
- allowed clarification and repair budget;
- evaluator-change policy;
- success threshold;
- transcript and custody requirements;
- negative controls or mutation controls where relevant;
- what full success licenses;
- what partial success licenses;
- what failure means;
- what failure does **not** retroactively erase.

At minimum, design gates for:

#### 1. Independent Implementation /0

The preferred strong design is a spec-only, independently seeded evaluator on a second substrate, tested against frozen normative vectors behind an exposure fence. Distinguish:

- a second codebase on the same Common Lisp substrate;
- a second implementation on a different Common Lisp implementation;
- a genuinely different language/runtime substrate;
- full-vector conformance versus coverage-bounded conformance;
- clean first pass, repaired pass, and evaluator-modified pass.

A full vector pass may license portable conformance **within vector scope** and the independence conditions actually met. It must not license semantic completeness, open-ended authoring, or latent-machine fitness.

#### 2. Independent Inhabitation /0

Specify how an author outside the construction loop receives only the public language materials and writes genuinely unseen programs without evaluator modification. Separate:

- ability to parse the guide;
- ability to predict semantics;
- ability to author a valid program;
- ability to diagnose a refusal;
- ability to revise within a declared budget;
- ability to compose more than a curated specimen.

Predefine how documentation defects, ambiguous requirements, invalid programs, correct predictions with failed execution, green executions with wrong predictions, and evaluator changes affect disposition.

#### 3. Generic/Open-Ended Authoring /0

Require diversity of tasks and authors sufficient to exceed a one-off inhabited specimen. State what would count as bespoke scaffolding, evaluator accommodation, task leakage, or post hoc task selection. One successful stranger is evidence of inhabitation, not automatically a civilization.

#### 4. Comparative Latent-Machine Authorship /0

Require preregistered task sets, equivalent exposures, model-family accounting, prompt and tool normalization, blinded adjudication where feasible, human or non-model baselines where relevant, and a declared statistical analysis. Distinguish absolute capability from comparative advantage. Do not let a campaign test “which model has memorized our house style?” while advertising “which language suits latent-space minds?”

Failure semantics are mandatory. Examples:

- If an independently seeded evaluator fails vectors, that is evidence against conformance of that implementation; it does not revoke Lisp+'s languagehood.
- If it passes only after access to reference implementation internals, it may improve interoperability but does not satisfy the independence gate.
- If an outside author produces a green program with an incorrect semantic prediction, execution succeeded but semantic transmission did not.
- If a correct program fails because public documentation omitted a governing rule, classify the documentation defect separately from the author's competence.
- If a campaign crosses some independence axes but not others, award only those axes.

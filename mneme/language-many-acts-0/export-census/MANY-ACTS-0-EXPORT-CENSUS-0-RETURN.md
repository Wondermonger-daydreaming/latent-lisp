## 2. How the expected table was materialized

Artifact: **`export-census/EXPECTED-EXPORTS.txt`** (blob
`78592073905450ff9afcd22dea53afbf53764fa1`), generated by
**`export-census/derive-expected-exports.sh`**.

The ruling requires the set be "materialized as an independent, sorted
expected-name table — not derived at runtime from the same package being
tested." The two sides of this census therefore have genuinely different
provenance:

- **Expected side** — read *statically* out of `package.lisp` **at the adopted
  coordinate**, via `git show <coord>:<path>`. Never the working tree, never a
  loaded image.
- **Actual side** — read at runtime from the live `LISP-PLUS-MANY-ACTS0`
  package after loading the system through ASDF.

Deriving the expected side from the package under test would prove only that a
set equals itself.

### 2.1 The extraction, shown

Two independent extractions are run and **compared**, with the script failing
closed (exit 3) if they disagree. One extraction is one unaudited opinion.

**Extraction A — regex sweep** of the exporting `defpackage`'s own lines:

```sh
git show 231873c7:…/package.lisp \
  | awk '/^\(defpackage #:lisp-plus-many-acts0$/,0' \
  | grep -oE '^[[:space:]]*#:[A-Za-z0-9+*<>=/-]+' \
  | sed 's/^[[:space:]]*#://'
```

The `awk` range begins at the *exporting* package. The other `defpackage` in the
file — `#:lisp-plus-many-acts0.program` — does not match, because the pattern is
anchored with `$` immediately after `many-acts0`. That second package exports
nothing and binds nothing; it is a name-homing namespace.

**Extraction B — reader-based structural walk.** The file is `READ` as data with
`*read-eval*` nil, the `DEFPACKAGE` form whose name-designator is
`LISP-PLUS-MANY-ACTS0` is located, and its `(:export …)` clause is walked
structurally. This catches what a line-anchored regex would silently drop: two
export names sharing one line.

Both extractions returned the same 38 names, with no duplicates. The sort is
`LC_ALL=C sort`, ascending by NAME — which places the three `+…+` constants
first, `+` being `0x2B`.

**Cardinality 38 is DERIVED from the set and recorded as an observation.** It is
never the test. No branch of the gate compares a count against a literal, and
the script does not know the number 38 in advance.

### 2.2 Designation method

Ruling 6 §3 B7 item 4 requires each export be bound "in its explicitly
designated sense: function, variable, condition class, structure type, or other
declared public category." Designations were derived by locating, in the R1
sources **at the same coordinate**, the form that actually defines each name.
Rules applied in order, first match winning:

| Category | Derived from |
|---|---|
| `condition-class` | `(define-condition NAME …` at top level, **or** membership in the `families` `macrolet` block |
| `structure-type` | `(defstruct (NAME …` |
| `variable` | `(defparameter NAME …` or `(defvar NAME …` |
| `function` | `(defun NAME …`, **or** `(:predicate NAME)` in a `defstruct`, **or** `:reader NAME)` in a condition slot |

Every row in the table carries its **defining file and line** and *how* the
designation was reached, so the classification can be re-checked without
trusting this document's summary. The script **fails closed** (exit 4) if any
name comes back `UNDERIVED`, and (exit 5) if any evidence cell lost its line
number — a table with a hole in it must not be emitted as though complete.

**The load-bearing case a naive method would have gotten wrong.** Six of the
eight condition classes — `ma0-source-refused`, `ma0-environment-refused`,
`ma0-authority-slot-unfilled`, `ma0-binding-refused`, `ma0-pattern-refused`,
`ma0-composition-divergence` — are minted inside a `macrolet` named `families`
(`ma0-structures.lisp:45–56`). **No `define-condition` line carries their
names.** A grep for `define-condition` alone would have found only
`ma0-refusal` and `ma0-environment-stale` and reported the other six as
undefined. The `families` block is harvested explicitly for exactly this reason.

Two derivation defects were found and fixed during construction, and are
recorded here rather than quietly repaired:

1. The three `+…+` constants first came back `UNDERIVED` — the regex escaper
   was not escaping `+`, so `+ma0-arms+` matched nothing. An under-escaped name
   is a designation hole wearing a clean exit. The escaper now escapes every
   non-alphanumeric, non-hyphen character.
2. `ma0-composition-divergence` first came back with an **empty line number**,
   because it is the last name in the `families` block and is followed by `))`
   rather than whitespace. The evidence column was lying about its own
   provenance; the pattern now accepts a closing paren, and a dedicated
   fail-closed check (exit 5) catches any recurrence.

## 3. The gate

| Artifact | Role |
|---|---|
| `export-census/ma0-export-census.sh` | driver; SBCL operation check; table identity; invokes the Lisp half |
| `export-census/ma0-export-census.lisp` | loads the live system, extracts the actual external set, compares, checks boundness |
| `export-census/derive-expected-exports.sh` | materializes `EXPECTED-EXPORTS.txt` from the adopted coordinate |
| `export-census/capture-tooth.sh` | transcript harness with a directly captured exit code |

The system is loaded **through ASDF** exactly as the lane's own runner does it
(`asdf:load-system "lisp-plus/many-acts-0"`, source registry rooted at
`experiments/latent-lisp`) — read out of `ma0-selftest.lisp` and `lisp-plus.asd`
rather than invented. The gate inherits the lane's SBCL-2.4.6 fail-closed law
rather than quietly widening it.

Three checks, all reported by name:

1. **Exact set equality** — prints `MISSING` (expected, absent) and `UNEXPECTED`
   (external, not on the roll) explicitly, each name on its own line.
2. **Boundness in the designated sense** — `function` ⇒ `fboundp` **and not** a
   macro **and not** a special operator (the lane mints no macro, contract §6,
   so a name that became one is a defect rather than a synonym for "callable");
   `variable` ⇒ `boundp`; `condition-class` ⇒ `find-class` **and** a subtype of
   `CONDITION`; `structure-type` ⇒ `find-class` **and** a subtype of
   `STRUCTURE-OBJECT`.
3. **Home-package guard** *(additional, not in place of any B7 requirement)* —
   every external symbol must be homed in `LISP-PLUS-MANY-ACTS0`. A same-named
   symbol homed elsewhere is a substituted citizen that a name-only roll would
   seat.

The gate also audits its own roll before using it: duplicate names, blank
designations, and a table that is not sorted are all findings. Exit codes: `0`
sentinel path only; `1` census findings; `2` the census could not be conducted
(bad table, load failure, unauthorized SBCL) — **a refusal to judge, never a
pass**.

hole), captured, then reverted with **blob identity proven restored**. The three

rather than one tooth three times.

**Tooth (a)** plants a name that is *genuinely fbound* — `ma0-refuse` is a real

it clean. Only set equality catches it.

**Tooth (b) is the ruling's own scenario, reproduced.** The planted source still
carries exactly 38 export lines; the transcript shows the gate printing

was hiding a substitution and the names caught it — the precise defect Ruling 6

**Tooth (c)** leaves `package.lisp` byte-identical at `a97d3c3e`, so **set

### 4.2 A defect in the FIRST capture attempt, recorded rather than buried

The first capture of tooth (a) wrote **`OBSERVED EXIT: 0`** into the transcript
for a run that had plainly refused and withheld its sentinel. The gate was
correct; **the transcript was wrong**. The exit code had been read with
`${PIPESTATUS[0]}` after an intervening `echo`, so it reported the echo's status
and not the gate's.

This is the more dangerous of the two possible failures — a transcript is
evidence, and evidence that misreports an exit code would have been filed as
proof. `capture-tooth.sh` was written to run the gate directly and capture `$?`
from the gate process itself, and **all four transcripts were captured with that
harness**. The line "captured directly from the gate process" in each transcript
refers to this.

## 7. Red flags and honest limits

1. **Same-author throughout.** The expected table, the gate, the teeth, and this
   return were produced by one agent. The two extractions cross-check each other
   but share an author, and the shared-root caution applies: agreement between
   two methods I wrote is weaker evidence than agreement between two hands.
2. **The gate proves set equality, never adequacy.** If `package.lisp` at the
   adopted coordinate exports the wrong thing, this census will certify the
   wrong thing exactly. It is a census, not an audit of the constitution.
3. **`38` appears in this document and in the sentinel as a derived observation.**
   It is never a threshold. Should the adopted coordinate's export set ever
   legitimately change, `EXPECTED-EXPORTS.txt` must be **regenerated from the new
   coordinate** and the change disposed of by the owner — never hand-edited to
   make the gate green. Editing the roll to match the citizens inverts the
   instrument.
4. **The load is not transactional.** The lane's own `lisp-plus.asd` commentary
   already states that a load dying mid-file would leave the package present and
   the lane half-built, and that its guard would not catch it. This census
   inherits that limit: it audits whatever the load produced.
5. **The home-package guard is an addition of mine**, beyond B7's five
   requirements. It is offered as a strengthening, discharges no ordered
   requirement, and earns no separate standing.
6. **P4/`p5`/`r1` program directories and the driver are not loaded** by
   `lisp-plus/many-acts-0`; `ma0-act-summary-verdict` has its only other
   reference in `ma0-driver.lisp`, which is why commenting it out was a clean
   tooth-(c) plant. The census speaks only for the loaded system.

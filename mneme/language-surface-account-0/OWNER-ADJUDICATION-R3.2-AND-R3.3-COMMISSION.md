## OWNER FINDING 1 — THE R3.2 BOOTSTRAP ELECTION IS NOT CLOSED

Reject the R3.2 claim that a constant `DEFGLOBAL` initializer is benign under
concurrent first `LOAD`s.

On the parcel's exact SBCL 2.4.6 semantics, two loaders can both complete the
defining form's unbound test before either initial-value write occurs. A pinned
interleaving then does this:

```text
both LOADs entered stale value form: T
A installed its mutex: T
B installed its distinct mutex: T
A mutex was clobbered: T
final cell is B mutex: T
```

The decisive sequence is:

1. A and B both observe the `DEFGLOBAL` cell unbound;
2. A performs the delayed initial `NIL` write and CAS-installs mutex A;
3. B later performs its already-authorized stale `NIL` write, erasing mutex A;
4. B CAS-installs a distinct mutex B.

CAS serializes CAS against CAS. It does **not** serialize an earlier defining
form's delayed write against a later CAS publication. The same class threatens
every separately published `NIL` or `0` state cell, not merely the mutex.

The existing eight-thread concurrent-first-load witness happened to observe one
favourable schedule. It did not pin the stale defining write and therefore is
not proof of the universal once-only law. Retain it as a useful contention
control, but stop presenting it as sufficient.

The later top-level `(load *sa0-identity-path*)` is a **sequential reload**. It
is not a re-entrant load. Correct every statement that calls it re-entrant.

## R3.3-A — MAKE ONCE-ONLY INITIALIZATION ACTUALLY ONCE-ONLY

Repair the non-production identity mechanism and its contract explanation so
the following law is true under arbitrary concurrent first-load interleaving:

1. There is one stable bootstrap carrier or equivalent atomic state machine.
   Its installation cannot be undone by any delayed defining-form initializer.
2. Exactly one winner gathers the epoch and constructs the complete state.
3. Epoch octets, epoch text, allocator synchronization, counter state, and the
   ready state are built privately and coherently published. No observer can
   see a mixture assembled from two initialization attempts.
4. Concurrent non-winners wait or retry through the documented synchronization
   and return only after observing the winner's complete ready state.
5. No first-load, reload, or re-entry path gathers a second epoch, resets the
   counter, replaces either synchronization object, or republishes readiness.
6. Initialization failure may not publish a half-state or a false ready state.

Do **not** repair this by changing `DEFGLOBAL` to `DEFVAR`, by adding a second
check around the same vulnerable cells, or by repeating the current
`DEFGLOBAL`-then-CAS pattern with more commentary. No cell carrying live
once-only state may remain vulnerable to a delayed unbound-to-bound definition
write after election/publication.

The implementation choice belongs to this probe round, but it must be made
explicit. A stable pre-existing CAS-able carrier, an atomic unbound-to-bound
primitive with demonstrated semantics, or another construction is admissible
only if its safety is argued from the actual SBCL operation and then measured
by the pinned teeth below. If implementation-specific machinery is used, name
it and record the exact SBCL version. “Atomic” is not an incense word; identify
the place, the competing writes, and the ordering relation.

Prefer one coherent state object/publication point over a constellation of
independently initialized globals. If a different design is chosen, prove why
late writes cannot split or erase the state.

### True same-thread re-entry

Bind re-entry operationally rather than poetically. A genuine re-entry is a
same-thread recursive `LOAD` of `probe-identity.lisp` triggered while the outer
load's initialization is still in progress, before ready publication.

It must not self-deadlock on the outer thread's mutex. It must not gather,
publish, reset, or allocate a second state. If the inner invocation is detected
as owner re-entry, it may take an explicitly documented probe-local deferred
path, but it may not claim that initialization is ready. The outermost
initialization remains responsible for the sole transition to ready. A
concurrent non-owner is not allowed to take that shortcut; it must wait for and
then observe the complete winning state.

METHOD (this header describes the script that wrote this file):
  Every count below is derived by scanning the named capture. Nothing is
  copied from a footer, a banner, or a previous artifact. The suites were
  not re-run; only bytes already on disk were read.
  Verdict lines are recognised by the two printer shapes live in this
  layer family — unnumbered  '  ok   <label>' / '  FAIL <label>'  and
  numbered  '  [NN] ok   <label>' / '  [NN] FAIL <label>'. Which shape a
  suite used is reported, not assumed.
  The footer is the LAST non-verdict line matching '<N> [checks]
  passed|produced / <M> failed'. The word decides the arithmetic:
  'passed' => total = N + M;  'produced' => total = N. Verdict lines are
  excluded from the footer search so a label quoting a tally cannot be
  mistaken for the tally.
  HARD-CODED, exhaustively: (1) the two capture filenames; (2) the verdict
  token set {ok, FAIL} and the two printer shapes above; (3) the footer
  word set {passed, produced}; (4) the SBCL implementation-failure marker
  patterns. NO expected check count, NO expected total, NO expected exit
  code and NO expected failure count appears anywhere in the script.
  KNOWN LIMIT, stated because it is real: for a suite using the UNNUMBERED
  printer a renamed verdict token cannot be detected structurally — it
  surfaces instead as 'footer == rendered' FAILING, which is checked. For
  the numbered printer the token is read off each line and checked exactly.
  Exit codes are read from RUN-EXITCODES.txt, written by the runner; if
  that file is absent the exit checks report UNKNOWN, never PASS.
